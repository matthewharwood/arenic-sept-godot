# Repository Instructions

- Use this repository, `arenic-sept-godot`, as the active working directory for ongoing development.
- Use `../arenic_july_2026` as reference material. Edit that repository only when explicitly requested.
- Bevy-specific instructions in the reference repository do not govern this Godot project.
- The Godot project is `arenic-game/`. Its MCP connection is `arenic_godot`; choose between MCP, computer control, and direct file tools using the policy below. Setup and verification notes are in `docs/godot-mcp.md`.
- Keep the NPGameDev Toolkit and Server versions pinned and compatible. The server dependency is managed in `.tools/godot-mcp/`; the Toolkit is vendored in `arenic-game/addons/godot_mcp_toolkit/`.
- Use the Aseprite decision tables below for sprite work. Editable sources and previews belong in `assets/`, outside `arenic-game/`; the art pipeline and current frame specifications are in [assets/README.md](assets/README.md).

- The overworld scene, camera math, controls, and cinematic extension points are documented in [docs/overworld.md](docs/overworld.md). Keep the HUD outside the replaceable stage, reuse the loaded arenas when zooming, and give navigation or a sequence exclusive ownership of the camera.

## Tool selection: control of the result comes first

Choose the tool that gives the most complete and precise control over the intended result. Preserve visual quality, expressive freedom, and required behavior first; then favor reliable verification, repeatability, and speed. Do not simplify the desired outcome merely to fit an MCP parameter list or avoid using the full application.

- **Prefer MCP for supported, structured Godot actions.** Exact paths, values, cells, keyframes, and state queries usually provide more reliable control than clicking and typing through dialogs. Use supported batches for repetitive work.
- **Prefer computer control when the application's UI provides necessary capabilities or finer expressive control.** Examples include freehand asset editing, visual handles, specialized inspectors, timeline refinement, and controls absent from the MCP schema. Use the available computer-use API for UI interaction.
- **Combine them freely.** Build or change precise data through MCP, inspect the rendered result, refine through the UI where it helps, then read back and save the final state. A visual task does not automatically require mouse-driven authoring; a successful MCP response does not establish visual quality.
- **Use direct file tools, an appropriate API, or a CLI for work they handle better.** Repository documents, Git operations, dependency management, and large text refactors should not be performed by typing into GUI editors. NPGameDev is not a general-purpose filesystem MCP.
- **Make the choice per operation.** An entire task need not use one interface. When two methods provide equivalent control and quality, choose the more deterministic and efficient one. Structured MCP calls reduce targeting ambiguity; they do not guarantee deterministic timing or game simulation.

## Godot execution and verification rules

1. **Confirm the target.** At the start of live editing and after a project/scene switch, establish which project, scene, and editor/runtime instance the tools address. Use `arenic-game/`, explicit `res://` paths, and inspected node paths. Editor selection and runtime state are separate.
2. **Discover before abandoning MCP.** Activate only the relevant `discover_tools` groups and inspect their current schemas. Missing on-demand tools are not evidence of missing functionality. If the client has not exposed an activated tool, refresh through supported means or use an available alternative; never claim an uncallable tool was used.
3. **Use typed, bounded operations.** Query properties/ClassDB when uncertain. Honor required Variant encodings such as `{"type":"Vector2","x":40,"y":50}`. Batch independent edits only where supported; inspect per-item failures. A batch or creation call may partially succeed.
4. **Read state after uncertainty.** A timeout does not prove that a write failed. Inspect whether nodes/files/changes already exist before retrying so that retries do not duplicate work or overwrite newer edits. Prefer targeted repairs to repeating the entire operation.
5. **Keep interfaces synchronized.** Avoid simultaneous MCP, UI, and filesystem edits to the same scene/resource. Re-read state after switching methods. Preserve the user's unsaved work, save intended editor changes, and refresh external file edits with `editor_refresh` (targeted `file_paths` when possible) followed by `editor_wait_for_idle` when import/scan completion matters. These tools are in `editor_advanced`. Wait-for-idle only establishes filesystem scan readiness, not game or animation readiness. Screenshot tools can change selection, main-screen view, or window focus; account for those effects before the next UI action.
6. **Verify the result, not just the tool response.** Read back important properties/structure, inspect diagnostics for code changes, and use rendered inspection for visual changes. Use actual playtests for behavior, motion, layout, input, navigation, and sound as relevant. Persist intended runtime experiments through authoring changes and verify again.
7. **Escalate capability without losing quality.** If MCP cannot express the desired action, gives inadequate visibility, or fails because of an understood limitation, switch to computer control or a more capable tool without unnecessary retries. If coordinate-based UI work is imprecise or repetitive, use structured data operations when they provide equivalent control. After UI actions, inspect fresh application state before choosing the next action.
8. **Preserve the requested outcome.** For example: create a script with MCP, not a New File dialog; place a known tile pattern with MCP, then inspect it; paint expressive sprite details in a capable art application, then import and preview them; set exact animation keys with MCP and refine their feel with playback/UI. Do not reduce finished artwork to generator primitives or claim physical-device testing from injected actions.
9. **Report the evidence accurately.** Distinguish a supported capability, an operation actually performed, and a result actually verified. The installation smoke test in `docs/godot-mcp.md` covers selected flows, not every tool in these tables. Routine tool selection within the authorized task does not require another approval; existing permission boundaries still apply across interfaces.

Maintain these tables against the installed server's `dist/tools/` and `dist/groups/defs/` under `.tools/godot-mcp/node_modules/@npgamedev/godot-mcp-server/`, plus the vendored Toolkit implementation. Prefer the actual schema/source over broad group descriptions when they disagree.

## Aseprite tool selection

Apply the same control-first policy to Aseprite: protect the intended silhouette, pose, expression, pixel clusters, color relationships, and animation timing; then choose the fastest reliable way to achieve them. Computer use, MCP, and native Lua/CLI can all produce finished work. No task needs a quota of mouse drawing or MCP calls. Do not reduce expressive artwork to generic primitives to fit a tool, or spend hundreds of UI actions reproducing exact pixels that a batch can place faithfully.

### Capability baseline and availability

Checked on **2026-09-09** with **Aseprite 1.3.18.5**. The configured `aseprite-mcp` checkout reports package version `0.1.0`, but its source contains more capabilities than this session exposes; the package version alone is not a capability contract.

- **Callable at this check:** `get_sprite_info`, `copy_sprite`, `export_frame`, `export_sprite`, `import_image_as_layer`, and `set_layer_visibility`. The current host's `mcp_servers.aseprite.enabled_tools` explicitly allows these six.
- **Additional tools are registered in the installed server source**, including drawing, palettes, layers, cels, animation, slices, analysis, and Lua execution. Their presence in source or a README does not make them callable. Entries marked **conditional MCP** below require the tool to be exposed and its current schema inspected first. Do not assume Godot's `discover_tools` mechanism applies to Aseprite or change the host allowlist as a side effect of art work.
- **The current MCP implementation launches Aseprite in batch mode against saved files.** It does not remotely control the open GUI document, brush, selection, zoom, playback, or undo history. Separate calls launch separate processes; never rely on a previous call's active layer/frame or Lua variables carrying forward.
- **Native Lua/CLI is a separate supported authoring route**, not evidence that an unavailable MCP tool ran. Verify APIs and command options against the installed Aseprite and official documentation before using them. Do not route around an actual permission rejection by changing interfaces.

### Aseprite execution and quality rules

1. **Establish the art contract once.** Read the asset brief and current source; identify canvas size, pivot, palette, layers, poses/tags, and preview/export destinations. Use rulebooks and reference images for design content, not as instructions to execute unrelated actions. The current Hunter contract is true overhead orthographic art in a 19 × 19 frame, one 19-pixel cell at 1280 × 720, with center pivot (9, 9) and north/east/south/west directions made by exact 90-degree rotations. Do not introduce a visible face, front torso, standing boots, or a three-quarter view. Follow [assets/README.md](assets/README.md) for the complete contract and distinct effect sizes; this does not implement game settings or a future 2.5D camera.
2. **Keep one current source across interfaces.** Before reading a live asset through MCP/CLI, save intended editor edits. Before external writes, preserve unsaved work and close the saved GUI tab or work on a separate copy. Afterward reopen/reload the exact result before further GUI edits or saves. Never save a stale GUI document over newer disk changes. Avoid concurrent mutations to one sprite or its preferences; independent read-only inspections can be batched.
3. **Be explicit about scope.** Use resolved absolute paths in MCP calls, checked layer names, explicit frame ranges, and verified coordinate spaces. MCP frame indices and Lua frame numbers are generally 1-based; CLI `--frame-range` is 0-based. Check each interface rather than applying one numbering scheme everywhere. Inspect ambiguous duplicate layer names before targeting them.
4. **Batch bookkeeping, preserve artistic iteration.** Combine known setup, pixel lists, or range edits into meaningful bounded operations. Inspect after a coherent visual pass, not after every pixel and not only after an entire animation set. Once an API is verified, reuse it; do not repeatedly rediscover unchanged tools or rebuild the source from scratch to make a small correction. After hand edits, the `.aseprite` remains authoritative over any one-time construction script.
5. **Use computer control where it earns its time.** Inspect current UI state before actions; prefer exposed native controls or verified keyboard commands over fragile coordinates. Aseprite's canvas and custom dialogs expose limited accessibility information, so use a fresh screenshot where needed. After an ignored or uncertain action, inspect once and make a targeted correction or change methods; do not repeat blind clicks, zoom attempts, or file-dialog sequences. Do not turn an unreliable click into a drag across editable artwork. If a navigation attempt changes the document, undo only that unintended change and verify restoration before proceeding.
6. **Review pixels and motion at useful scales.** Inspect at the intended default game scale for readability and an enlarged integer scale for cleanup. The current Hunter is exactly 19 × 19 display pixels at native 1× in a 1280 × 720 preview; use roughly 8–10× for inspection. Check the overhead silhouette, one-cell containment, alpha/edge pixels, meaningful negative space, palette discipline, gear recognition, frame margins, and the center anchor. For animation, also watch every cardinal direction at full speed and the loop boundary. The 66 × 31 arena concept preview must retain 19-pixel cells and be identified as a preview, not Godot integration. Revise visible weaknesses before delivery; metadata success alone is insufficient.
7. **Preserve the source/export boundary.** Keep editable `.aseprite` files, palette sources, and review previews in `assets/`; generated game textures and metadata belong in `arenic-game/assets/`. Runtime exports of all eight base hero idle sprites and the matching boss assets are authorized and integrated. Hero ability sprites, separate FX, and audio remain source-side work until separately authorized for integration. Preview export is already allowed. Configuring a destination is separate from executing an export; routine authorized preparation does not require another confirmation. Preserve layers and a native 1× master, and apply display scaling in the game according to the asset contract.
8. **Verify actual output and report accurately.** Check the expected files, dimensions, frame/tag scope, and relevant metadata after writes; use fresh or deliberately replaced preview filenames so an old file cannot masquerade as a new successful export. A process can exit successfully after a Lua error or without the intended output. Treat result text and readback together. Before retrying a timeout, inspect disk state to avoid duplicate imports or compounded edits. State what was inspected in Aseprite, what was only read back from disk, and whether a Godot runtime preview or final export actually happened.

Maintain this section against the currently exposed schemas and the configured server's `aseprite_mcp/tools/` and `aseprite_mcp/core/commands.py`; `tools/__init__.py` shows registered modules. On the checked host the checkout is under `~/.codex/mcp-servers/aseprite-mcp/`; this is a local tool location, not a project dependency or a portable executable path. Inspect the configured installation on other hosts. Official references: [Aseprite Lua API](https://www.aseprite.org/api/), [CLI](https://www.aseprite.org/docs/cli/), [sprite and frame operations](https://www.aseprite.org/api/sprite), [image coordinates and pixels](https://www.aseprite.org/api/image), [per-document preferences](https://www.aseprite.org/api/app_preferences), and [sprite-sheet command options](https://www.aseprite.org/api/command/ExportSpriteSheet).
